Case study · 2026 · Live on this site

A chatbot that answers questions about me — grounded in this website, not in guesses.

The chatbox in the hero of this homepage is a retrieval-augmented assistant: a Cloudflare Worker gateway in front of self-hosted n8n, vector search over this site's own content, and a Groq-hosted LLM that is only allowed to answer from what was retrieved. It was built, broken, debugged, and then left running — answering visitors right now.

Cloudflare WorkersVectorizeWorkers AID1n8nRAGGroqCloudflare Tunnel

Hands-on personal project. This is self-study, not paid client work — and it documents a live system, not a mockup. The chatbox at the top of the homepage is this exact pipeline.

01Business problem

A portfolio is a one-way brochure: visitors read, but cannot ask. The information they want — what was built, how it works, what the automation lab actually contains — is scattered across sections, and the old contact form only answered one question at a time, by email, hours later.

I wanted the opposite: a visitor types "What is the AI Agent Conference?" and gets a real answer immediately — from my content, without inventing facts or leaking an API key into the browser.

02Goal & acceptance criteria

Goal: a public chat widget that answers questions about me using only this website's content, safely and cheaply.

  • Answers must come from retrieved site content — the assistant admits when it does not know.
  • Prompt-injection attempts must not produce invented facts, prices, or claims.
  • No secret ever reaches the browser; every privileged call is server-side.
  • Abuse-resistant: per-visitor rate limit, message length cap, session validation.
  • Graceful degradation — if any part is down, the site stays fully usable.
  • Free-tier friendly: Workers free plan, Workers AI neurons, Groq's free developer tier.

04Input payload

The browser only ever sends two fields. The session ID is a stable per-tab UUID kept in sessionStorage and must match a strict pattern before anything else happens.

{
  "message": "What is the AI Agent Conference?",
  "sessionId": "3f8a2c1e-9b4d-4e7a-8c2f-1d5b9a7e6c40"
}

06Credentials & authentication

Shared gateway secret

One long random value stored as a Worker secret and as an n8n header — both directions of the n8n ↔ Cloudflare traffic authenticate with it. It has never been in frontend code.

Webhook URL

The n8n endpoint URL is also a Worker secret — nothing about the private topology is visible in the page source.

Browser

The browser holds zero keys. It posts two JSON fields to same-origin /api/chat and nothing else.

Secrets hygiene

All values live in Cloudflare secrets / n8n credentials; nothing committed to git.

08Transformations

  • Contract adaptation: n8n returns {reply}; the gateway normalizes it (accepting the earlier answer shape too) before responding to the browser.
  • Output hygiene: the answer is trimmed and capped at 4,000 characters; the sources array is capped at five.
  • Input hygiene: messages trimmed and capped at 2,000 characters; session IDs must match ^[A-Za-z0-9_-]{6,64}$.
  • Render safety: the UI writes with textContent only — no HTML from the model can ever execute.

12Root causes

#Root cause
E1The chatbot workflow was built but never activated — n8n only serves production URLs from active workflows.
E2The secret existed in the dashboard but the running Worker did not have it — the wrong resource had been configured.
E3Same class as E2: a secret missing at runtime makes the gateway refuse early by design, before touching n8n.
E4n8n listens on localhost:5678 inside Docker on my PC — the Cloudflare edge physically cannot connect to another machine's localhost.
E5Two halves of the system were specified separately; the response field name drifted between them. Caught by an integration test before it reached visitors.

13Fixes

#FixWhy it works
E1Activate the workflow (editor toggle).n8n registers production webhook routes only for active workflows.
E2–E3Upload both secrets directly to the Worker (wrangler secret put). Secrets survive deploys.The gateway's early-exit check now passes and the header matches on both sides.
E4Cloudflare Tunnel: a local cloudflared process exposes only the n8n endpoint over public HTTPS; the Worker secret points at it.Outbound tunnel connection needs no port forwarding; the editor UI stays private.
E5Gateway accepts reply first with answer as fallback.Adapter at the boundary absorbs contract drift; both shapes tested.

14Final workflow — live

The system currently answering on the homepage: knowledge base of 10 chunks from this site's homepage (the featured systems, the lab, the design archive), a two-gateway layout — public chat gateway on this Worker, private RAG gateway on a second Worker — and the full guardrail suite passing live: grounded answer, honest "I don't know", injection refused.

Visitor → Worker gateway → Tunnel → n8n → Vectorize search → Groq → Worker → chatbox

Known gaps, kept on purpose: the corpus is one page deep so far; chat-message logging is not yet recording (the save leg is next); the tunnel URL is ephemeral until a named tunnel replaces it.

15Lessons learned

  • The Cloudflare edge cannot reach localhost — "it works on my machine" is a whole deployment phase when the server is your desktop.
  • Contract mismatches between two separately-built halves only surface in end-to-end tests. Mock tests caught the reply/answer drift before a visitor did.
  • Missing secrets should fail loud and early — the gateway's "warming up" response made the diagnosis a one-look job instead of a mystery.
  • Grounding rules work: the model refused to invent pricing and admitted not knowing a pizza preference, because retrieval had nothing to offer.
  • Once again: valid workflow JSON is not automatically a correct automation — the pipeline only became real after it was broken on purpose.
